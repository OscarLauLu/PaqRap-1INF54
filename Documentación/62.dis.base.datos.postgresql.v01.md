## 1. Criterio de mapeo clase → tabla

| Elemento del diagrama de clases | Tratamiento en la BD | Razón |
|---|---|---|
| Clase con identidad propia y atributos | Tabla | Caso general |
| Enum **sin** atributos propios (`EstadoPedido`, `NivelCriticidad`, `EstadoOperativo`, `TipoMovimiento`, `EstadoRuta`, `TipoEscenario`, `EstadoEjecucion`, `TipoAlerta`) | `CREATE TYPE ... AS ENUM` nativo de Postgres | Son solo un conjunto cerrado de valores, no cargan datos adicionales |
| Enum **con** atributos propios (`TipoEntrega` tiene `horasPlazo`; `TipoAveria` tiene `descripcion`, `horasNoDisponible`, `horasPermanenciaLugar`, `trasladoACentral`) | Tabla catálogo (fila = valor del enum + sus atributos) | Un `ENUM` de Postgres no puede cargar columnas adicionales |
| `Ubicacion` (value object: `posX`, `posY`) | Columnas `_x`/`_y` inlineadas en la tabla dueña | No tiene identidad ni ciclo de vida propio; siempre pertenece a otra entidad |
| `Nodo` de `RedVial` | No se persiste | La retícula es regular (70×50 km, nodo cada 1 km): las coordenadas válidas se derivan de `red_vial_config`, no hace falta materializar ~3 500 filas |
| `Almacen` (abstracta) + `AlmacenCentral` + `AlmacenIntermedio` | Una sola tabla `almacen` con columna discriminadora `tipo_almacen` y columnas específicas de intermedio en NULL para el central (herencia de tabla única) | Solo 2 subtipos y pocas columnas exclusivas; separar en 3 tablas agregaría joins sin beneficio real |
| `Planificador`, `Visualizador`, `CargadorArchivos` | No se persisten | Son clases de comportamiento (servicios de aplicación), sin estado propio que sobreviva a una ejecución |
| `AlgoritmoACO.matrizFeromonas` | No se persiste | Estructura de trabajo en memoria, se reconstruye en cada ejecución; persistirla no aporta valor y crece con el tamaño de la red |
| `MotorSimulacion` + `RelojSimulado` (composición 1 a 1) | Una sola tabla `simulacion_ejecucion` con las columnas del reloj inlineadas | `RelojSimulado` no tiene existencia fuera de su `MotorSimulacion` dueño |
| Relación `Alerta` originada por `AlmacenIntermedio` **o** `UnidadTransporte` | Columnas `origen_tipo` + `origen_id` (referencia polimórfica, sin FK nativa) | Postgres no soporta FK que apunte a "una de varias tablas"; se valida en la capa de aplicación |
| `Trasvase "1" --> "1..*" Pedido` | Tabla puente `trasvase_pedido` | Relación N:M real (un trasvase puede redistribuir varios pedidos) |
| `Bloqueo "0..*" --> "1..*" Tramo` | Tabla puente `bloqueo_tramo` | Relación N:M real |

Fuera de alcance de este diagrama (y por lo tanto de esta BD): autenticación/autorización de usuarios. El caso no define roles de acceso ni login; el requisito de "múltiples dispositivos conectados simultáneamente" (R5) es sobre visualización concurrente, no sobre cuentas de usuario.

-- 1. TIPOS ENUM NATIVOS (enums sin atributos propios)
-- ------------------------------------------------------------
CREATE TYPE estado_pedido        AS ENUM ('REGISTRADO','PLANIFICADO','EN_RUTA','ENTREGADO_PARCIAL','ENTREGADO','CANCELADO');
CREATE TYPE nivel_criticidad     AS ENUM ('VERDE','AMBAR','ROJO');
CREATE TYPE estado_operativo     AS ENUM ('DISPONIBLE','EN_RUTA','EN_MANTENIMIENTO','AVERIADA');
CREATE TYPE tipo_movimiento_inv  AS ENUM ('CARGA','DESCARGA','RECARGA_DIARIA','LIBERACION_RESERVA');
CREATE TYPE estado_ruta          AS ENUM ('PLANIFICADA','EN_EJECUCION','REPLANIFICADA','COMPLETADA','CON_ALERTA');
CREATE TYPE tipo_escenario       AS ENUM ('DIA_A_DIA','SIMULACION_5D','COLAPSO_LOGISTICO');
CREATE TYPE estado_ejecucion     AS ENUM ('CONFIGURADA','EN_EJECUCION','FINALIZADA','DETENIDA_POR_COLAPSO');
CREATE TYPE tipo_alerta          AS ENUM ('UNIDAD_AVERIADA','OCUPACION_ALMACEN','PLAZO_INCUMPLIDO','VIA_BLOQUEADA');
CREATE TYPE tipo_almacen         AS ENUM ('CENTRAL','INTERMEDIO');
CREATE TYPE origen_alerta_tipo   AS ENUM ('ALMACEN','UNIDAD_TRANSPORTE');

-- ------------------------------------------------------------
-- 2. TABLAS CATÁLOGO (enums CON atributos propios + catálogos fijos)
-- ------------------------------------------------------------

CREATE TABLE tipo_entrega (
    codigo          VARCHAR(20)   PRIMARY KEY,   -- REGULAR_36H, PRIORIZADA_18H, PRIORIZADA_12H, PRIORIZADA_8H, PRIORIZADA_4H
    horas_plazo     SMALLINT      NOT NULL CHECK (horas_plazo IN (4,8,12,18,36))
);

CREATE TABLE tipo_vehiculo (
    codigo                  VARCHAR(2)    PRIMARY KEY,   -- TA auto, TM moto, TB bicicleta
    nombre                  VARCHAR(30)   NOT NULL,
    capacidad_maxima        SMALLINT      NOT NULL CHECK (capacidad_maxima > 0),
    velocidad_promedio_kmh  NUMERIC(5,2)  NOT NULL CHECK (velocidad_promedio_kmh > 0),
    costo_por_km            NUMERIC(6,2)  NOT NULL CHECK (costo_por_km >= 0),
    actualizado_en          TIMESTAMPTZ   NOT NULL DEFAULT now()
);

CREATE TABLE tipo_averia (
    codigo                      VARCHAR(10)  PRIMARY KEY,  -- TIPO_1, TIPO_2, TIPO_3
    descripcion                 VARCHAR(120) NOT NULL,
    horas_no_disponible         SMALLINT     NOT NULL,
    horas_permanencia_lugar     SMALLINT     NOT NULL,
    traslado_instantaneo_central BOOLEAN     NOT NULL
);

CREATE TABLE turno (
    id           SMALLSERIAL  PRIMARY KEY,
    hora_inicio  TIME         NOT NULL,
    hora_fin     TIME         NOT NULL,
    UNIQUE (hora_inicio, hora_fin)
);
-- 3 filas fijas: 07:00-15:00, 15:00-23:00, 23:00-07:00

-- 3. CONFIGURACIÓN DE LA RED VIAL (fila única)
-- ------------------------------------------------------------

CREATE TABLE red_vial_config (
    id                   SMALLINT  PRIMARY KEY DEFAULT 1 CHECK (id = 1),
    ancho_km             SMALLINT  NOT NULL,   -- 70
    alto_km              SMALLINT  NOT NULL,   -- 50
    separacion_nodos_km  SMALLINT  NOT NULL DEFAULT 1
);

CREATE TABLE tramo (
    id                    BIGSERIAL     PRIMARY KEY,
    nodo_origen_x         SMALLINT      NOT NULL,
    nodo_origen_y         SMALLINT      NOT NULL,
    nodo_destino_x        SMALLINT      NOT NULL,
    nodo_destino_y        SMALLINT      NOT NULL,
    longitud_km           NUMERIC(5,2)  NOT NULL CHECK (longitud_km > 0),
    bidireccional         BOOLEAN       NOT NULL DEFAULT TRUE,
    UNIQUE (nodo_origen_x, nodo_origen_y, nodo_destino_x, nodo_destino_y)
);
CREATE INDEX ix_tramo_origen  ON tramo (nodo_origen_x, nodo_origen_y);
CREATE INDEX ix_tramo_destino ON tramo (nodo_destino_x, nodo_destino_y);

CREATE TABLE bloqueo (
    codigo              VARCHAR(20)  PRIMARY KEY,
    fecha_hora_inicio   TIMESTAMP    NOT NULL,
    fecha_hora_fin      TIMESTAMP    NOT NULL CHECK (fecha_hora_fin > fecha_hora_inicio),
    activo              BOOLEAN      NOT NULL DEFAULT TRUE
);

CREATE TABLE bloqueo_tramo (
    bloqueo_codigo  VARCHAR(20)  NOT NULL REFERENCES bloqueo(codigo) ON DELETE CASCADE,
    tramo_id        BIGINT       NOT NULL REFERENCES tramo(id) ON DELETE CASCADE,
    PRIMARY KEY (bloqueo_codigo, tramo_id)
);

-- ------------------------------------------------------------
-- 4. CLIENTES Y PEDIDOS
-- ------------------------------------------------------------

CREATE TABLE cliente (
    id_cliente              VARCHAR(20)  PRIMARY KEY,
    nombre                  VARCHAR(120) NOT NULL,
    ubicacion_entrega_x     SMALLINT     NOT NULL,
    ubicacion_entrega_y     SMALLINT     NOT NULL
);

CREATE TABLE pedido (
    codigo                  VARCHAR(20)   PRIMARY KEY,
    id_cliente               VARCHAR(20)   NOT NULL REFERENCES cliente(id_cliente),
    tipo_entrega_codigo      VARCHAR(20)   NOT NULL REFERENCES tipo_entrega(codigo),
    cantidad_unidades        INT           NOT NULL CHECK (cantidad_unidades > 0),
    cantidad_entregada       INT           NOT NULL DEFAULT 0 CHECK (cantidad_entregada >= 0),
    fecha_hora_registro      TIMESTAMP     NOT NULL DEFAULT now(),
    plazo_limite_entrega     TIMESTAMP     NOT NULL,
    fecha_hora_entrega       TIMESTAMP,
    destino_x                SMALLINT      NOT NULL,
    destino_y                SMALLINT      NOT NULL,
    estado                   estado_pedido NOT NULL DEFAULT 'REGISTRADO',
    CHECK (cantidad_entregada <= cantidad_unidades)
);
CREATE INDEX ix_pedido_estado       ON pedido (estado);
CREATE INDEX ix_pedido_plazo        ON pedido (plazo_limite_entrega);
CREATE INDEX ix_pedido_cliente      ON pedido (id_cliente);

-- ------------------------------------------------------------
-- 5. FLOTA
-- ------------------------------------------------------------

CREATE TABLE conductor (

    nombre   VARCHAR(120)  NOT NULL
);

CREATE TABLE unidad_transporte (

    ubicacion_actual_y   SMALLINT,

    dada_de_baja         BOOLEAN            NOT NULL DEFAULT FALSE

    CHECK (
        (tipo_almacen = 'CENTRAL'    AND capacidad_maxima IS NULL AND stock_actual IS NULL)
        OR
        (tipo_almacen = 'INTERMEDIO' AND capacidad_maxima IS NOT NULL AND stock_actual IS NOT NULL

    codigo           VARCHAR(20)          PRIMARY KEY,
    almacen_codigo   VARCHAR(20)          NOT NULL REFERENCES almacen(codigo),
    fecha_hora       TIMESTAMP            NOT NULL DEFAULT now(),
    tipo             tipo_movimiento_inv  NOT NULL,
    cantidad         INT                  NOT NULL CHECK (cantidad >= 0),
    ruta_codigo      VARCHAR(20)                                     -- FK diferida a ruta (ver sección 7)

    fecha_hora_fin            TIMESTAMP,

    unidad                   VARCHAR(20)  NOT NULL,
    fecha_hora_calculo       TIMESTAMP    NOT NULL DEFAULT now()
);
CREATE INDEX ix_indicador_resultado ON indicador_desempeno (resultado_codigo);

CREATE TABLE alerta (
    codigo               VARCHAR(20)         PRIMARY KEY,
    tipo                 tipo_alerta         NOT NULL,
    mensaje              VARCHAR(300)        NOT NULL,
    fecha_hora_generacion TIMESTAMP          NOT NULL DEFAULT now(),
    atendida             BOOLEAN             NOT NULL DEFAULT FALSE,
    origen_tipo          origen_alerta_tipo  NOT NULL,
    origen_id             VARCHAR(20)        NOT NULL   -- almacen.codigo o unidad_transporte.codigo, según origen_tipo
);
CREATE INDEX ix_alerta_atendida ON alerta (atendida);
CREATE INDEX ix_alerta_origen   ON alerta (origen_tipo, origen_id);

## 4. Decisiones de diseño relevantes para la sustentación

1. **Herencia de `Almacen` como tabla única.** Se evaluaron 3 estrategias clásicas (tabla única, tabla por subtipo, tabla por clase concreta). Con solo 2 subtipos y 3 columnas exclusivas de `AlmacenIntermedio`, la tabla única evita joins innecesarios en la consulta más frecuente del sistema ("¿qué almacén tiene stock para este pedido?"), a costa de algunas columnas NULL para `AlmacenCentral`. El `CHECK` de la tabla `almacen` impide estados inconsistentes (p. ej. un central con `capacidad_maxima` fijada).

2. **`Ubicacion` no es una tabla.** Es un objeto de valor (value object) sin identidad propia: siempre "pertenece" a otra entidad y se compara por sus coordenadas, no por un ID. Modelarla como tabla aparte solo agregaría joins sin ganar integridad real, porque el rango válido de `(x, y)` de todas formas se valida contra `red_vial_config` en la capa de aplicación.

3. **`Nodo` no se persiste.** La retícula es regular y completa (70 × 50 km, nodo cada 1 km): cualquier par `(x, y)` dentro de esos rangos es un nodo válido. Materializarlos como filas no aporta información que no esté ya en `red_vial_config`.

4. **Referencia polimórfica en `alerta`.** `Alerta` puede originarse en un `AlmacenIntermedio` o en una `UnidadTransporte`. PostgreSQL no permite una FK que apunte "a una de varias tablas posibles", así que se usa el patrón `origen_tipo` + `origen_id`, validado en la capa de aplicación (o con un trigger `CHECK` a futuro si se requiere integridad estricta a nivel de BD).

5. **`matrizFeromonas` y las clases de comportamiento puro no se persisten.** `Planificador`, `AlgoritmoACO` (salvo sus parámetros configurables), `Visualizador` y `CargadorArchivos` son servicios de aplicación sin estado de negocio propio — su "estado" son los datos que leen y escriben en las demás tablas.

6. **Claves naturales sobre claves surrogadas donde el diagrama ya define un `codigo`.** Clases como `Pedido`, `UnidadTransporte`, `Ruta`, `Averia`, etc. ya declaran un atributo `codigo` o `idCliente` como identificador de negocio en el diagrama de clases; se usó ese mismo valor como PK (`VARCHAR`) en vez de introducir un `id` numérico paralelo, para no duplicar identidad. Las clases sin código de negocio explícito (`ParadaRuta`, `AsignacionTurno`, `IndicadorDesempeno`, `Turno`, `ParametrosSimulacion`, `ConfiguracionSemaforo`, `SimulacionEjecucion`) usan `SERIAL`/`BIGSERIAL`.

7. **Fuera de alcance:** tablas de usuarios/autenticación (el caso no las define) y una tabla `nodo` materializada (ver punto 3).
